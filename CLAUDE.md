# Anubis

Anubis is an exciting, revoluationary project that's meant to be a framework that's extremely comparable to the (Ruby Bullet Train framework)[https://bullettrain.co].

However, it's core stack differs dramatically from Bullet Train. Here we use a rust-first ecosystem, with a full Rust backend.
Additionally, we use a React.js client side rendered SPA with HeroUI and TailwindCSS.
We don't use the same Ruby and SSR stack that Bullet Train uses, but offer as much as we can of everything else.

Additionally, we're tied closely to Jalapeno Labs and use:
- (Arsox Satellites)[https://github.com/JalapenoLabs/arsox-satellites] (for remote LLM job management)
- (UI Kit)[https://github.com/JalapenoLabs/uikit] (for re-usable UI components)
- (CLI)[https://github.com/JalapenoLabs/cli] (for utils like eslint standardization)
- (Brand)[https://github.com/JalapenoLabs/brand] (for Jalapeno Labs branding + styles + themes)
- (Github Actions)[https://github.com/JalapenoLabs/github-actions] (Shared, re-usable github actions workflow items and flows)

For full details, reference the @./README.md
We have a @./docs folder, for all documentation.
We use Github Issues for tracking tech debt and future work, and use milestones as "epics" for grouping a collection of tasks together.
We have @./bullet_train which has documentation of bullet train, in which we fully model and we submodule the main branch of their repository at bullet_train/bullet_train for reference.
We have a full research report about what bullet train is, generated by Claude web as a deep research job, outputted in @./bullet_train/bullet-train-deep-research.md for reference.
That report covers the framework's identity and history, current MIT/open-source licensing (including the fully open-sourced former Pro tier), modular gem architecture, Super Scaffolding code generator, team/membership multi-tenancy model, roles/permissions via CanCanCan, front-end stack (Tailwind + Hotwire + ERB), auto-generated REST API, developer workflow, deployment options, community health, real-world adopters, comparisons with Jumpstart Pro and vanilla Rails, demo resources, a categorized feature list, staged recommendations for a senior frontend engineer, and caveats around stale pricing sources and front-end lock-in.

# Blessed architecture decisions

These are decided and current. Full detail lives in @./docs (architecture.md, tenancy.md, scaffolding.md, api.md, server.md, sessions.md, webhooks.md, notifications.md, audit.md, billing.md, oauth-server.md, mcp.md, testing.md).

- **Backend**: Rust on tokio, Axum + tower + hyper. World-class idiomatic Rust is the bar.
- **ORM**: Diesel + diesel-async. Chosen for maximum compile-time typing; no stringly SQL, no runtime query surprises.
- **Datastores**: PostgreSQL required (system of record, durable job queue, and sessions by default). Redis optional: `REDIS_URL` moves realtime (the event sequence, the replay buffers, and pub/sub fanout) into it, and `SESSION_STORE=redis` (which requires `REDIS_URL`) keeps browser sessions there instead of in Postgres. The store is its own setting because realtime in Redis without Redis sessions is a reasonable deployment. Unset, nothing touches Redis. Never the system of record, and nothing in the durable job queue goes near it.
- **Sessions**: one session store, `auth::session::Sessions`, enum-dispatched over Postgres and Redis, and the only way a session is created, read, listed, or revoked. Behaviour is identical in both: a 256-bit token in an `HttpOnly` cookie, only its SHA-256 at rest, a fixed 30-day life, sign out, sign out one session from the list, every other session ended by a password change, every session ended by a password reset, a temporary password, or account deletion, the list oldest first with the current one marked, and the `session.created`/`session.revoked` audit events. **Signing out everywhere is decided in Postgres, never in the store**: every account has `users.session_generation`, every session is stamped with the generation it was created under, and a session signs nobody in unless its stamp *equals* the account's current generation, which every lookup reads with the account (never cached beside the session). A sign-out-everywhere moves the account to a new generation as the last statement of the transaction that changes the credentials (a password change re-stamps the kept browser first), and the store is only swept after the commit, as housekeeping, deleting only sessions stamped with the generation that revocation ended (a sweep may run after a later sign-out-everywhere, so any other stamp may be a session that later one kept); so eviction, a snapshot or failover rollback, or a change of `SESSION_STORE` cannot revive an ended session. **Generations are drawn from the `session_generations` sequence, never computed as the old one plus one**: a sequence never reissues a value a rolled-back transaction drew, so a Redis re-stamp left behind by a failed commit carries a value the account never takes and stays dead through every later reset. Stamps compare for equality because drawn values only identify. A session is stamped with the generation read with the credentials the sign-in checked (`User` carries it; an MFA challenge carries its first factor's), and creating it re-reads the generation under `FOR SHARE` and refuses the sign-in with `401` when it moved, so a sign-in racing a sign-out-everywhere always loses. A password change is conditional on the generation its session was validated under and answers `401` before writing when a reset committed in between, so it never overwrites the reset's password (`409` when another change from the same browser committed first, since that browser is still signed in). Signing one session out is a delete in its store alone, so a Redis that loses that write revives that one session until sign-out-everywhere. Whatever a sign-in spends or creates in Postgres (a new account and its organization, a reset link, a recovery code, an emailed code, a passkey ceremony and its counter, an invitation) is spent in the same transaction as the session write, which comes last, so a store failure spends nothing and a failed sign-up leaves no account; an OpenID Connect sign-in restarts instead, since the provider's code is spent by the exchange. `server::harden` puts the configured store on every request, so the setting is the whole opt-in; a request that bypassed `harden` reads Postgres (logged at debug), and the auth routes refuse with a logged `500` a request whose store disagrees with `SESSION_STORE`. `serve` asks a Redis store whether it can hold sessions before binding and refuses to boot, naming `SESSION_STORE`, when it does not answer, is older than 7.0, or has a memory limit with an evicting policy (read from `INFO memory`, which managed Redis answers even where it refuses `CONFIG`); it warns below an append-only file. An application pairing `harden` with `serve_with_shutdown` skips that check. Reads of the store (the per-request check, logout, the list, revoke-by-id) take the pool and touch Redis before checking a Postgres connection out. Redis keys live under `anubis:sessions:`: a token key holding the session as JSON and expiring with it, and a per-user sorted-set index whose expiry only extends (`EXPIREAT NX` then `GT`). A Redis holding sessions belongs to one deployment, at 7.0+, `noeviction`, with an append-only file, and not Cluster. `anubis doctor` reads the two settings with the configuration's own parser and asks Redis exactly what the boot asks, through the same `auth::inspect_redis` (hidden from the docs). The starter's compose Redis runs an append-only file on a volume. See [sessions.md](docs/sessions.md).
- **Packaging**: one Cargo package (`anubis/`, library + CLI binary), one npm package (`frontend/`, `@jalapenolabs/anubis`), one thin starter template (`starter/`), all in this monorepo. No crate/package sprawl. The crate **publishes as `anubis-framework`**, because an unrelated 2019 crate holds `anubis` on crates.io, and **every visible name stays `anubis`** through Cargo's dependency renaming: `[lib] name` and `[[bin]] name` are `anubis`, the workspace declares `anubis = { path = "anubis", package = "anubis-framework", version = "..." }`, and a stamped application declares the same key over its own source, so `use anubis::` and the `anubis` command are untouched. Only the two commands that name a package to the registry differ: `cargo install anubis-framework` and `cargo update -p anubis-framework`. An `anubis` entry missing the `package` key resolves the squatter, so `anubis upgrade` refuses it and prints the line to write.
- **Releasing**: the crate and the npm package are **published, not consumed from git**, and they ship together from one tag under one version, because an application depends on both and a version naming half a release resolves for nobody. `.github/workflows/release.yml` fires on `v*`: it checks that the tag, `[workspace.package] version`, the `anubis` workspace dependency, and `frontend/package.json` all agree, and that the workspace dependency still renames the package `anubis/Cargo.toml` declares (`scripts/check-release-version.sh`), runs the full gates and the four drift checks, vendors the starter, packages, then uploads to crates.io and npm and cuts a GitHub Release with generated notes. Running the workflow by hand is a rehearsal: every gate, no upload. Neither registry allows republishing a version, so a half-finished release is recovered by a patch bump, never a retag; the GitHub Release is created last so the releases page never names a version only one registry carries. `CARGO_REGISTRY_TOKEN` and `NPM_TOKEN` are the two repository secrets. **The starter is vendored into the crate at publish time**: `anubis new` stamps from a template embedded at build time, and `cargo package` reaches nothing above `anubis/`, so `scripts/vendor-starter.sh` copies the committed tree to a gitignored `anubis/starter/` that `build.rs` prefers over `../starter`. An `include` list in `anubis/Cargo.toml` is what packages it (an include list makes cargo walk the filesystem instead of asking git, which would report a gitignored path as nothing), and manifests inside the packaged tree carry prefixed names (`Cargo.toml.vendored`, `workspace-Cargo.toml`, `backend-Cargo.toml`) because cargo prunes any directory holding a `Cargo.toml` as a nested package. `anubis/tests/packaging.rs` fails on either trap. See [ci.md](docs/ci.md#releases).
- **API contract**: REST at `/api/v1`, OpenAPI 3.1 via utoipa, generated TypeScript client (ky route functions + SWR hooks). No protobuf. The **application owns its OpenAPI document**: it declares the version's identity and merges the framework's half plus one line per scaffolded model, mounts the result with `api::v1::router_with`, exports it from its own binary, and generates the client with `anubis client generate-ts --from`. A platform token acts with its team's `admin` role, through the same compiled `roles.yml`.
- **Codegen**: Bullet Train's philosophy 1:1. Living templates (real compiling code, not a DSL), magic anchor comments, generated code is owned by the app. `anubis scaffold` generates backend + frontend + tests + docs in one command. `anubis eject <Component>` is the ownership escape hatch, Bullet Train's `bin/resolve --eject`: it copies a field component out of the installed npm package into `frontend/src/anubis/`, stamps its provenance, and rewires the app's imports. The ejectable surface is the field component library only; the API client, realtime client, and hooks stay framework-owned, because a copy of those forks a wire protocol rather than a style. The templates are `CreativeConcept`, `TangibleThing`, `GranularDetail`, `IncidentalLinkage`, `PeripheralNotion`, and `HypotheticalSenderWebhook` in `starter/`, compiled and integration-tested in CI; the anchor vocabulary is tabulated in `docs/scaffolding.md`. **Ownership runs three deep** (`Team`, `<Parent>,Team`, `<Parent>,<GrandParent>,Team`) and a fourth link is refused by name, because a depth is a living template rather than a flag: a name-for-name transform of a two-table query never produces a three-table one. The team is **read off the chain's root in the same query**, never denormalized onto the row, so a generated handler authorizes every hop as a join and a crafted cross-tenant path answers `404` at the first link it cannot reach. Every model owns a show page; a team-owned model also owns a list page and the navigation entry, and a nested model at either depth owns the section component its parent's show page renders. That nested show page is what the depth below it attaches to. Apps own their migrations and `schema.rs`; the starter backend is a library plus a thin binary so tests drive the real routers.
- **Associations**: `super_select` spells both of Bullet Train's, and the suffix decides which. Plural `<other>_ids` is a **has-many-through**, whose values are rows in a join model an earlier `scaffold join` created. Singular `<name>_id` is a **belongs_to**: a real nullable `UUID REFERENCES <targets> (id) ON DELETE SET NULL` column (an assignment is a pointer, not a dependency, so removing a person empties the field rather than being blocked by it), indexed, plus `valid_<attribute>s` and `<attribute>_labels` on the model, an options endpoint at `/account/teams/{team_id}/<owners>/options/<attribute>` (keyed by owner and attribute so two assignments never collide), validation before the insert, and a joined `<name>_label` on the view so screens render a name rather than a uuid. `{source=...}` is Bullet Train's modifier and means what it means there, namely where `valid_*` reads from: `team.memberships` is the framework roster (the default and only source for `class_name=TeamMembership`, Bullet Train's signature "assign to a membership, not a user" pattern, served by `TeamMembership::valid_for_team` and `labels_for` because a framework table cannot join an application one), `team.<others>` is the target model's own team-owned records (the default otherwise), and anything else is refused by name. A belongs_to target must be team-owned, and neither association can be declared at `scaffold model` time. Both `scaffold join` and `belongs_to` still refuse a side owned through a parent, at any depth, because one comparison is what decides whether a submitted id is this tenant's; lifting that needs a scope query per side and is separate work. **Deferred with a written design**: `buttons`/`options` fields with fixed translatable option lists, which is a separate item from `{source=...}`.
- **Background jobs**: durable Postgres queue, no Redis in the durability path. Enqueue rides on the caller's connection so it commits with the domain write. At-least-once delivery, quadratic retry backoff, then a `dead_jobs` table an operator reads. Jobs declare their own queue; a worker serves exactly the queues it has handlers for.
- **Webhooks, outgoing**: a team subscribes an HTTPS endpoint to event types under `/developers`; `anubis::webhooks::emit` writes a delivery row and a delivery job per subscriber **on the caller's connection**, so an event commits with the write that caused it. Event types are `<model>.<action>` (`created`, `updated`, `destroyed`); the catalog is the application's models, so the framework validates the shape. Payloads are the model's `View`, the same serializer `/api/v1` answers with. Delivery is the framework's own job on its own `webhooks` queue: HMAC-SHA256 over `<timestamp>.<body>` in `anubis-webhook-signature: v1=<hex>`, at-least-once, retried on the queue's backoff, then marked `dead`. Endpoint secrets are **encrypted** with `secret_box`, not hashed, because signing needs the raw value; they are shown exactly once. Generated models emit from the shared create/update/destroy functions, so both surfaces emit identically. See [webhooks.md](docs/webhooks.md).
- **Webhooks, incoming**: `anubis scaffold webhook <Provider>` generates a receiver for one third party. A received request is **stored first and processed afterwards**: the unauthenticated endpoint at `/webhooks/<provider>` writes one row (payload, headers, verified, received_at, processed_at, error) and enqueues its processing job **in one transaction**, then answers `200`, because a provider punishes a slow or failing receiver with retries and eventually disables it. The table is owned by nobody (a provider names no team), so it takes no `roles.yml` entry, no ownership chain, and no `/api/v1` surface. A failed signature check is **recorded in `verified`, never used to refuse the request**: rejecting at the edge destroys the evidence that explains what happened. `anubis::webhooks::signature::verify_hmac_sha256` is the provider-agnostic primitive every scheme ends in; the generated `verify_signature` wires the generic hex-of-the-body default and documents Stripe's, GitHub's, and Anubis's own. Processing runs on its own `incoming_webhooks` queue through `register_jobs` in the app's `lib.rs`. Receivers are deliberately **not rate limited**: the auth budgets are sized for humans, and refusing real events is what puts an endpoint on a retry schedule. Two functions are deliberate blanks the run names in its output, `verify_signature` and `act_on`. See [webhooks.md](docs/webhooks.md).
- **Realtime**: Server-Sent Events. `anubis::realtime::Channels` publishes, and browsers listen over one session-authenticated stream at `GET /realtime?channels=...`, read by the `@jalapenolabs/anubis` client with `fetch` rather than `EventSource` so a stream that changes its channels can still resume. Channel names are structured and carry their own authorization rule: `team:{team_id}:{topic}` admits the team's members through the `TeamMember` guard's own rule (suspensions deny), `user:{user_id}:{topic}` admits that user, `resource:{id}:{topic}` is served only by the application's own endpoint, and a refused channel reads exactly as a nonexistent one. **Events carry payloads and ids**: every publish takes the next id of one deployment-wide sequence (`{epoch}-{sequence}`) and is kept in its channel's replay buffer (64 events, or `ChannelsBuilder::retain` per topic, within a 64 MiB budget that lets go of whole channels, least recently published first). A reconnect sends `Last-Event-ID` and receives what it missed; **a replay is exact or the channel opens with a `reset`**, sent wherever the buffers no longer vouch for the gap (per-channel floor, global watermark, foreign epoch; a Redis restart or failover, seen as a new `run_id`, starts a new epoch so a rewound sequence never reissues ids), on a fresh channel so it reads its state once live, and to listeners as a discriminated union beside events. Each stream opens with refusals, resets, the replay, and a `live` frame carrying the cursor, sends a heartbeat every 20s, and ends after five minutes (re-authorizing on reconnect), on the server's drain, or when 256 events behind, its channels released on schedule even when its client stops reading. An account holds at most 32 streams and 512 channels across them per process (`429` past that), each counted until its connection closes, so no account can fill the process's 16,384-channel table for everyone else, and a client that stops reading holds only its own account's share until the proxy's send timeout closes it. Channel names must arrive in their canonical spelling. Applications stream from their own endpoints with the `Subscriber` extractor (the session check is part of the type) and `Channels::stream`, with `backfill()` for a log tail. Streams need no untimed declaration: the timeout clocks only the handler, which a test pins. In process by default; `REDIS_URL` moves the sequence, the buffers, and the fanout into Redis (one Lua script per publish, so pub/sub order is sequence order; one channel per `SUBSCRIBE`, pipelined, so each confirmation answers its own command; every script bounded per call, an epoch change included). The Redis user needs `INFO` and the framework's pub/sub channels (`+@all -@dangerous +info &anubis:realtime:*`), both checked at startup. **Production serves HTTP/2 at the edge, behind a proxy with a send timeout**, because HTTP/1.1's six connections per origin are shared by every tab and each tab holds a stream, and the proxy is what closes a client that stopped reading. See [realtime.md](docs/realtime.md).
- **Notifications**: a framework-owned inbox, one row addressed to one person. `anubis::notifications::notify` is the single emission call and is `webhooks::emit`'s sibling: the insert rides the caller's connection, so a notice commits with the write that caused it. The row carries a machine-readable `kind` (`<subject>.<event>`), a stored English `title`/`body`/`href` (written once, because the record it names may later change or be deleted), `read_at`, and an optional `team_id`; a translated application looks its copy up by `kind`. Notifications are **addressed, not owned**, so there is no `roles.yml` entry, no ownership guard, and no `/api/v1` surface (a bearer token acts as a team, and a team has no inbox). The REST surface is three session-authenticated routes under `/account`: list (unread first, then newest, paginated, with the whole inbox's unread count), mark one read, mark all read; another user's id answers `404`. Realtime is a **ping, not a payload**: `notify` enqueues `PingRecipient` on the caller's connection and a `Pinger` on the `notifications` queue publishes `user:{user_id}:notifications` after the commit, because a publish inside the transaction would announce a notice that may roll back; the bell refetches on every ping and every reset. The framework emits six notices: invitation received (to an invited address that already has an account, never carrying the claim token), invitation claimed (to the admins of what was joined), roles changed (to the member), a webhook endpoint that stopped answering (to team admins, once per endpoint per day, leaving the endpoint active), and the wallet's low balance and failed recharge (to the organization's billing members). **The scaffolder emits nothing**, the same line drawn for billing limits. The bell is `NotificationBell` in `@jalapenolabs/anubis`, mounted by the stamped `AppShell`, taking its four strings as `labels` and its navigation as `onNavigate` because the package imports neither i18next nor a router. Deliberately out of scope: email digests, per-type preferences, and reply-by-email. See [notifications.md](docs/notifications.md).
- **Audit log**: append-only, and on from the first request. `anubis::audit::record` writes one row through the caller's own connection, so an event commits with the write that caused it exactly as `webhooks::emit` and `notifications::notify` do; nothing in the framework updates or deletes a row, no endpoint offers either, and the table carries no `updated_at`. A row says where (`team_id` or `organization_id`, at most one, and neither for an account-level act such as a password change), who (`user_id` plus a **copied** `actor_name`, so a deleted account still reads), what (`action`, `subject_type`, `subject_id`, plus a copied `subject_label`), what moved (`changes` as `{field: {old, new}}`), and under which request (`request_id`). A handler takes the `audit::Context` extractor, which never fails, and attributes it with `.by(&user)` or `.by_application(&app)`; `Context::system()` records a null actor for a job. **Framework surfaces record themselves**: tenancy (organization and team create/rename/destroy, invitation created/claimed/revoked, member added/role changed/removed/left), platform invitations (the same verbs plus `invitation.resent`, on the subject type `PlatformInvitation`), and the auth-sensitive acts (password changed, temporary password set, TOTP enrolled/disabled, passkey added/removed, session revoked, account deleted), and the profile picture (avatar uploaded/removed, and refused by an application's image screen). **Scaffolded models ride the shared create/update/destroy functions webhooks emit from**, so every generated model is audited with zero per-model code; the update's change set is `Changes::between` over the Diesel record, which is why a column `scaffold field` adds is audited the moment it exists. **Secrets are absent because they are never serialized**, not because anything strips them: a change set is computed from the same view `/api/v1` answers with, and credential events record an empty set. Actions are the bare lifecycle verbs for a model (`created`, `updated`, `destroyed`) and dotted verbs for the framework (`member.role_changed`), so the two vocabularies cannot collide. Reading is two routes under `/account`, outside `/api/v1` because the log is an operator's view rather than part of the versioned contract: `GET /teams/{team_id}/audit-events` (admin role, paged, filterable by `subject_type` and `actor_id`) and `GET /audit-events` (the caller's own account events, which is what makes the credential rows readable). The screen is `/teams/:teamId/audit-log`. Deliberately out of scope: retention, export, an organization roll-up screen, and diffing associations. See [audit.md](docs/audit.md).
- **Tenancy**: User -> TeamMembership -> Team -> Organization, plus OrganizationMembership for org-level roles. Resources chain ownership to a Team; assignments target TeamMemberships. Personal org + default sub-tenant + default team auto-created at signup. Billing attaches to the Organization. **A third tier, the SubTenant, sits between Organization and Team**: it is what GCP calls a project and GitHub a repository, it owns the work and its own membership, and a Team either scopes itself to one sub-tenant (`teams.sub_tenant_id`) or stays organization-level and is inherited by all of them. The tier is additive: an organization always has one, and an ownership chain ending in `Team` is untouched. **`anubis::tenancy::resolve_sub_tenant_access` is the one function that decides who reaches a sub-tenant and with which roles, and nothing re-derives it**: an organization admin bypasses, a full member cascades, a guest (`organization_memberships.access = 'guest'`) reaches only explicit grants, an organization-level team is inherited while a scoped one never leaks, and the resolved roles are the union of every grant that applies. **A suspension (`suspended_at` on either membership) is a deny**, checked before every grant and outranking the admin bypass, honored by all three guards. `SubTenantMember` is the guard, answering `404` for unreachable and nonexistent alike. Still to come on [#93](https://github.com/JalapenoLabs/Anubis/issues/93): the scaffolder's `SubTenant` template family, and the management endpoints and screens that create sub-tenants, manage a roster, scope a team, and suspend a member. See [tenancy.md](docs/tenancy.md).
- **Permissions**: single `roles.yml`, compiled to both a Rust authorization module and a TypeScript UI-affordances module. A role may declare `scopes` (`platform`, `organization`, `sub_tenant`, `team`) naming the tiers it may be granted at; omitting it means every **tenancy** tier, so a file written before the sub-tenant or platform tier keeps its meaning. Scopes say where a key attaches, not what it grants, so they do not travel through `includes`.
- **The platform tier**: the deployment itself, above every organization in it, and not a tenant. It has no entity, no roster, and no id in a route, so a platform role is held on the user (`users.platform_roles`) rather than on a membership. `platform` is the one scope outside the default set, because a `default` role that silently reached the whole deployment would be the worst possible default. `guard::PlatformMember` admits an account holding any platform-scoped role and answers every other signed-in account `404`, the same opacity the tenant guards give an unreachable id; admission is not permission, so a handler still calls `require`. The first operator is appointed by the environment, since nobody exists to appoint them: `ANUBIS_INITIAL_ADMIN_EMAIL` and `ANUBIS_INITIAL_ADMIN_PASSWORD`, applied by `platform::ensure_initial_admin` right after migrations, validated at config load. **The seed is a grant, never a reset**: an address with no account gets one (email pre-verified, personal organization bootstrapped, `roles::OPERATOR_ROLE` granted), an existing account is granted the role and keeps its password, and an account that already holds it is left alone with nothing written. Revoking is deliberately absent, because a boot that demoted the only operator would lock the deployment out of itself. Grants record `platform.roles_changed` in the audit log, attributed to the system, on neither a team nor an organization. **Operators bring people in by invitation**, through `anubis::platform::Accounts` called from the application's own guarded routes (every method takes the `PlatformMember`): an invitation is a `platform_invitations` row, never an account, until the invitee accepts by choosing a password, which creates the account with its email verified, grants the role the invitation carried, and signs it in, all in one transaction. One live invitation per address (partial unique index), refused for an address that has an account, links live 24 hours (`INVITATION_TTL_HOURS`), a resend replaces the token hash so the old link dies, and revoking marks the row. The invitee's half is `POST /auth/invitations/lookup` and `/accept`, token in the body, every unusable token answering one `400`. **Temporary passwords**: `Accounts::set_temporary_password` sets a generated password returned once (never stored, logged, or audited), revokes every session, and sets `users.password_change_required`; the `CurrentUser` extractor then answers every route `403` with the code `password_change_required` (`ApiError::with_code`), and only `SignedIn` routes (`GET /auth/me`, `POST /auth/change-password`) admit the account until it changes the password, which refuses the current one and clears the flag. Disposable-domain rules are the application's. Still to come: operator listing and grant/revoke endpoints and screens, and platform-scoped models in the scaffolder. See [tenancy.md](docs/tenancy.md#the-platform-tier).
- **Billing**: subscriptions attach to the **Organization**, and plans are configuration, not rows. `config/billing.yml` is compiled to a typed `PlanSet` and validated at boot exactly as `roles.yml` is: one plan per entry with a key, a name, per-interval Stripe price ids, and an app-defined `limits` map. Exactly one plan sells no prices (leaving aside the paid plan) and is the **free plan**, which is what an organization **paying for nothing** is on, so plan resolution is total. Stripe is the system of record for money: Stripe Checkout takes every purchase, the Stripe Billing customer portal takes every change to a plan subscription, and `subscriptions` plus `subscription_items` are the projection the app authorizes from (Stripe's status words verbatim). **An organization holds many subscriptions**: at most one live **plan subscription** (no subject, names its plan) and any number of **subject subscriptions**, each paying for one of the application's records named by `subject_type` and `subject_id` (the audit log's pair) and naming no plan; a check constraint holds the two kinds apart, and two partial unique indexes enforce one live plan subscription per organization and one live subscription per record across every organization. Every subscription carries its **line items** (`subscription_items`, one per Stripe price: item id, price, quantity, null for metered), so an add-on is an item beside the thing it adds to. **Plan resolution is one function** (`limits::plan_in_force`, behind `Limits::plan_for`, the endpoints, and seat enforcement), three steps in order: a granting live plan subscription decides (an explicit plan purchase is never overruled); otherwise an organization **paying for anything**, a granting subject subscription or a wallet balance above zero, is on the plan `paid_plan` names in `billing.yml` (optional; it may sell no prices, and is never the free plan); otherwise free. The billing `GET` reports the deciding step as `plan_source` (`plan_subscription`, `paid_status`, `free`), and seats follow the plan, so an organization whose credit runs out drops to the free plan's seats without anyone being removed. **The prepaid credit wallet** is on when `billing.yml` has a `wallet` section (`name`, `currency`, `minimum_top_up_micros`, optional `low_balance_micros`): every amount everywhere is integer **micro-units** (1 USD = 1,000,000, the unit in every name, `_micros`), `wallets` holds one balance per organization and `wallet_entries` is the **append-only ledger** it caches (credits positive; kinds `top_up`, `recharge`, `spend`, `refund`, `refund_reversal`; each entry carries its `balance_after_micros` and a `position` that orders the chain), and every write takes the wallet's row lock first and never calls Stripe while holding it, so the balance always equals the ledger's sum. `anubis::billing::Wallets::spend` is the application's spend API, on the caller's connection, idempotent per organization on a caller-supplied key (same key and amount replays, a different amount is `409`), and it **drains to zero and never below**: a spend larger than the balance takes what is left and reports `uncovered_micros`, one at zero is refused `402` (`Error::is_insufficient`) with nothing written, which is how the application learns the wallet ran dry, in the same call, and where it stops usage; only a refund takes the balance below zero, since the money already left. **Top-ups** are Stripe Checkout in `payment` mode (`POST .../wallet/top-up`, at least the minimum, whole cents, optionally saving the card off-session), credited once per PaymentIntent from the amount Stripe received, bound to the organization whose customer paid, from whichever of `checkout.session.completed`, `checkout.session.async_payment_succeeded`, or `payment_intent.succeeded` lands first. **Auto-recharge** (`PUT`/`DELETE .../wallet/auto-recharge`, needs a saved card, amount at least the minimum and the threshold): the spend landing below the threshold arms one attempt on the wallet row under the lock and queues `RechargeWallet` on the `billing` queue (one dip, one charge); the job lists the customer's payments for the attempt id before charging off-session, keyed by attempt and revision, so a lost answer is found rather than charged twice, a saved `5xx` re-keys, and a decline or other definite refusal turns auto-recharge off, audits `wallet.auto_recharge_failed`, and tells the billing members, never looping; a refund never arms one. **Refunds** are one debit per Stripe refund id while pending or succeeded and a `refund_reversal` if it later fails, read back with every refund of the payment after converging the payment itself, so order never matters. Notices `wallet.low_balance` (crossing the mark, not while auto-recharge can run) and `wallet.recharge_failed` go to the billing members through `notify`; credits, refunds, reversals, and auto-recharge changes are audited (`wallet.topped_up`, `wallet.recharged`, `wallet.refunded`, `wallet.refund_reversed`, `wallet.auto_recharge_changed`, `wallet.auto_recharge_failed`), spends are not (the ledger is their record); all ride the write's own transaction. The wallet in the billing `GET` and the paged ledger (`GET .../wallet/entries`) are `admin` or `billing` only; reconciliation converges wallet payments and their refunds too; without Stripe the wallet reads, held credit still spends, and the writes answer `503`. **`anubis::billing::Subscriptions`** is what an application calls for subject subscriptions: `checkout` opens Stripe Checkout with every line item and the subject in the subscription's metadata (refusing a record already paid for with `409`, return links built from `APP_URL` plus an application path), `change_items` takes declarative `ItemChange::set(price, quantity)` / `remove(price)` sent as one update on Stripe's default proration, and `cancel` ends one at period end or now. A change locks the subscription row for its whole length (`SELECT ... FOR UPDATE SKIP LOCKED`, answering `409` rather than queueing while the row is being written, so waiters cannot drain the pool), reads the subscription back from Stripe, sends the smallest request that reaches what was asked (a repeat sends nothing) with an idempotency key hashed from the request and the row's last write, and writes Stripe's answer plus an audit event (`subscription.items_changed`, `subscription.canceled`) in that transaction; a record another organization pays for answers not found. Stripe replays a key's first answer for a day, refusals included, so a refused update moves the row's revision (the read-back makes a fresh key safe); an answer marked `Idempotent-Replayed` is read back rather than trusted, and a change it shows no longer holds answers `409` under a fresh revision; an unknown outcome (a lost answer, a Stripe 5xx, a key still in use) is read back and, when Stripe shows the change in place, written and audited; and the change runs on its own task so a caller that times out can never leave the row locked. `checkout` and `change_items` read each price from Stripe first and refuse one that does not bill every month or year, while the projection records whatever Stripe reports (a quarterly price on its unit) so a cancellation is always recordable. **The framework serves no route that starts or changes a subject subscription**, deliberately: only the application knows whether a record is the organization's, who may spend on it, and which prices it sells, and an endpoint taking price ids from a browser would let a customer buy any price in the account; `subscriptions::Error` converts into `ApiError` so the application's route forwards it with `?`. The Stripe client is **hand-written** over the existing `reqwest` + rustls stack, fourteen calls, because a generated SDK would model the whole API to serve them. `STRIPE_SECRET_KEY` is the switch: unset, everyone is on the free plan, reads still answer, and the writes answer `503`; production without it warns at startup. Endpoints are org-scoped under `/billing`, reading open to members and spending (and reconciling) gated on the `admin` or `billing` role. The **lifecycle** is framework-owned: Stripe posts to a framework-mounted receiver at `POST /webhooks/stripe-billing` (named so an app scaffolding its own `/webhooks/stripe` never collides), which verifies Stripe's `t=,v1=` signature strictly, refuses what does not verify with `400` storing nothing, stores what does in `stripe_billing_events` (event id unique, so a redelivery is one row and one job), and queues `ProcessStripeEvent` on the `billing` queue. Processing **reads the subscription back from Stripe** rather than trusting a possibly stale payload (a deletion is trusted, being final), and the upsert applies only when the event is not older than the one already applied (`subscriptions.stripe_event_at`), so out-of-order delivery cannot undo a cancellation; the items are written in the same transaction behind the same guard, deleting any Stripe no longer lists, and a long embedded item list is read to its end first. The subject comes from the subscription's metadata. A write that read Stripe directly (reconciliation, `SyncSeats`, an application's change) is **stamped when its read began, in whole seconds**, so a newer event always applies and a cancellation in the same second is never dropped; reconciliation and `SyncSeats`, which hold no row lock, are stamped a second earlier still so they lose every tie with an event; and the upsert never replaces a terminal status with a live one, since Stripe never revives a subscription. `SyncSeats` sends nothing when Stripe already bills the seats or the subscription is over. `STRIPE_WEBHOOK_SECRET` is the receiver's switch and is refused without the API key. Missed events are repaired by reconciliation, `Reconciler::reconcile` and `POST /billing/organizations/{id}/reconcile`, which pages through the customer's subscriptions at Stripe and converges each, rows and items, in its own transaction, naming any it cannot record while repairing the rest. **Limits** are the plan's `limits` made real by `anubis::billing::Limits`: a limit written as a bare count is **hard** and its creation past the ceiling answers `409` naming the plan ("The Free plan's projects limit of 3 is reached. Upgrade to add more."); written as `{count, enforcement: soft}` it never refuses and the screen reports the overage. Bullet Train's split, kept. A limit a plan does not name is unlimited. **`seats` is the one limit the framework enforces itself**, at invitation creation, inside the invitation's transaction under the organization lock; a seat is a person counted once by email across org memberships, claimed team memberships, and live invitations. Every other limit is the application's to check at its own creation choke points with `limits.check(connection, org, name, held)` (the scaffolder does not write it: which model is metered, and under what name, is a product decision). **Per-seat pricing** is a `per_seat` flag on a price: checkout buys the seats in use, and every membership change queues `SyncSeats` on the `billing` queue, which sets the quantity on the plan subscription's item billing that price, keyed, on Stripe's default `create_prorations`, and writes the answer back. A flat-priced app never queues one. **`anubis billing generate-ts`** is the fourth generator, rendering `billing.yml` into `plans.generated.ts` (ordered plans, prices, limits, highlighted, free, paid), drift-gated in CI like the other three, in the framework's workflow and in the stamped one. The billing `GET` answers the plan, `plan_source`, and the plan subscription to every member, and every live subscription with its items, and the wallet, to `admin` or `billing` only (`null` for anyone else, since a record's subscription names the record and its prices). The **billing screen** is `/organizations/:organizationId/billing` (where Stripe returns the browser), rendering the plan subscription while an application renders its records' subscriptions where those records live: current-plan card with status chip, `past_due` warning, cancel-at-period-end notice, period end and seat usage; the plans grid from the generated catalog; the portal link and a reconcile action, all three drawn only for `admin` or `billing`; a billing-disabled card when `STRIPE_SECRET_KEY` is unset; the credit card (balance, warnings, the top-up and auto-recharge dialogs for the billing roles) linking the paginated ledger at `/organizations/:organizationId/billing/activity`; and the `?checkout=` and `?top_up=success|canceled` landings, trusted for nothing but a sentence. What the module deliberately leaves out: card forms, plan-change screens, invoices, tax, dunning email, proration policy, time-based usage limits, any periodic reconciliation sweep, application changes to a plan subscription's items (the portal's job), a hook telling the application a record's subscription changed, usage reporting for metered items, and on the wallet, promotional grants, expiry, overdrafts, disputes, tax on credit, and a card list. See [billing.md](docs/billing.md).
- **Serving**: one framework call, `anubis::server::serve`, owns production behavior; `main` only composes routers. It mounts liveness `/healthz` (no I/O) and readiness `/readyz` (database pool, 2s), and layers, outermost first: a server-minted request id returned as `x-request-id`, request tracing, security headers, opt-in CORS, and a 30s per-request timeout answering `503` in the `ApiError` shape. **A route whose duration is the client's, an upload above all, may be declared untimed** through `server::Hardening::untimed` with `serve_with`/`harden_with`: the timeout is skipped for exactly that method and matched route, everything else in the stack still applies, and the timeout itself stays a constant rather than a knob. `SIGTERM` and ctrl-c drain in-flight requests for 25s, inside Kubernetes' default grace period, and tell every request the drain started so realtime streams end at once instead of holding it. See [server.md](docs/server.md).
- **Security posture**: `nosniff`, `strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, and a full **content security policy** on every response, rendered once at startup: `default-src 'none'` with `script-src 'self'` (the Vite build emits no inline script and compiles nothing at runtime, so no `'unsafe-eval'`), `style-src 'self' 'unsafe-inline'` (React Aria and Motion write stylesheets into the document as they run and some carry no nonce, so a nonce would break what it did not cover), `img-src 'self' data: blob:` (the avatar picker previews through `URL.createObjectURL`), `font-src 'self'`, `connect-src 'self'` (the realtime stream is a same-origin `fetch`), `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`. `CSP_ALLOWED_SOURCES` extends the seven fetch directives with host sources, validated at boot, and can never widen `default-src`, `base-uri`, `form-action`, `frame-ancestors`, or add a keyword such as `'unsafe-eval'`. The layer fills the header in rather than overwriting, so a handler may carry its own: exactly one does, the Scalar API reference at `/api/v1/docs`, which loads from a CDN. HSTS in production only, and only over https. CORS is strict same-origin until `CORS_ALLOWED_ORIGINS` names exact origins, validated at config load; credentials are never allowed cross-origin, so the bearer-token `/api/v1` surface is the cross-origin consumer and cookies stay same-origin.
- **Supply chain**: `cargo audit` and `yarn npm audit` run on every CI push, non-blocking for now; see [ci.md](docs/ci.md) for when they flip blocking.
- **Secrets at rest**: hashing is the default (passwords, tokens, recovery codes). Secrets the app must read back, such as TOTP seeds, are encrypted with pure-Rust AES-256-GCM (`anubis::auth::secret_box`) under `ANUBIS_SECRET_KEY`: base64 for 32 bytes, required in production, with a public development fallback so `yarn dev` stays zero-config. Stored values are versioned (`v1:<nonce>:<ciphertext>`). `anubis secret generate` mints a key (stdout carries the key alone, guidance goes to stderr) and `anubis doctor` warns when the variable is unset and fails when it holds a value that cannot be a key. Keys are zeroized on drop. Rotation is one-way by design: every value sealed under the old key stops opening, so TOTP enrollments are discarded and those users enroll again. A dual-key read path (previous key tried on failure, re-sealing as values are read) is future work.
- **Stamped applications**: `anubis new` hands over a repository that is ready to run and ready to merge. It formats the Rust it stamps, the same pass `anubis scaffold` runs and for the same reason: the application's crate name sorts wherever it sorts inside the templates' `use` blocks (`axum` falls after `acme` and before `zebra`), so no template order is right for every name, and a stamped tree has to pass the `cargo fmt --check` its own CI runs first. Beyond the manifests and pins it stamps `.github/workflows/ci.yml` (GitHub-hosted runners, fmt, clippy, tests against Postgres, the frontend job, and all three drift checks: roles, plans, and the API client), and `.env.example`. Development configuration is environment-driven: `yarn dev` copies `.env.example` to `.env` when absent, loads it with `dotenv-cli`, and hands the same file to `docker compose --env-file`, so credentials are written once. The database is named after the app and each stamp mints its own development password. Apps are private by default (`"license": "UNLICENSED"`); `--license mit` writes an MIT LICENSE. Templates ship no lockfiles: the app pins by committing `Cargo.lock` and `yarn.lock` in its first commit, under toolchains that `rust-toolchain.toml` and `packageManager` pin exactly. The monorepo starter runs the same `.env` flow, because it is the template.
- **Versioning and upgrades**: pre-1.0, a `0.x` minor may break and a patch never does, and every release ships notes naming the breaks and the steps they take by hand. The crate and the npm package ship as one release carrying one version, which `scripts/check-release-version.sh` cross-checks before the release workflow publishes anything. Applications take a release with **`anubis upgrade`**: it rewrites the `anubis` requirement in `backend/Cargo.toml` and the `@jalapenolabs/anubis` requirement in `frontend/package.json` (string surgery keeping each range operator, refusing a shape it does not recognize rather than guessing), runs `cargo update -p anubis-framework` and `yarn install`, re-runs all three drift generators in process so the CLI's own version is what regenerates, and prints the release notes URL. `--to <version>` names the target and never reaches the registry; `--dry-run` prints the plan and writes nothing. The structural promise is that **framework behavior lives in versioned dependencies, so an upgrade is never a starter-template merge**, which is Bullet Train's biggest documented cost. The trade is deliberate: the files `anubis new` stamped, the CI workflow and the Dockerfile among them, belong to the application forever, and a release that changes a template names the edit in its notes instead of merging it. An application tracking the framework from git has no version to bump and is told exactly that. The crate publishes as `anubis-framework` because `anubis` on crates.io is held by an unrelated crate published in 2019, so an application's entry must carry `package = "anubis-framework"`; the command refuses one that does not, and verifies the repository a crates.io entry declares before moving an application onto it. See [upgrading.md](docs/upgrading.md).
- **Connected clients (OAuth server and MCP)**: a deployment is an OAuth 2.1 authorization server for programs acting as a person, and serves an MCP endpoint those programs call. `anubis::oauth_server` is **built here, not adopted**: no maintained Rust crate implements the MCP profile (oxide-auth covers none of metadata documents, Protected Resource Metadata, resource binding, `iss`, or loopback port matching for both hosts). **Clients are public only**: **Client ID Metadata Documents** first (what Claude and Codex pick when the metadata says `client_id_metadata_document_supported`, `none` auth, `S256`, and `authorization_response_iss_parameter_supported`, all four advertised), fetched over https with every resolved address required public, the connection pinned to the checked address, no redirects, 5 KB, cached 5 minutes to a day and forgotten once stale when no grant or pending request holds it, loopback http allowed outside production only, and `/oauth/authorize`, which triggers the fetch, held to thirty an hour per client address; **Dynamic Client Registration** as the fallback, bounded by ten an hour per client address, public clients and the three grants only, and unused registrations swept after a day (unless a device flow they started still waits) with a 5,000-row ceiling answering `503`. Redirect URIs are https or loopback http, matched exactly except the port of a loopback URI (RFC 8252). **Authorization code with PKCE `S256`**, and the **device authorization grant** (RFC 8628) for a program with no browser; each client declares its grants in `oauth_clients.grant_types` (none declared means the code flow, `refresh_token` always present), only a code-flow client must register a redirect URI, and each endpoint refuses a client that did not declare its grant with `unauthorized_client`. `/oauth/authorize` stores the validated request and redirects to the SPA's `/consent?request=<id>` (`CONSENT_PATH`, a backend/frontend contract like the billing return), failures before the redirect URI is trusted land on `/consent?error=<code>` and after it go to the client with `state` and `iss`. **A grant is one person's consent for one client** and every token descends from it: codes (2 minutes), access tokens (1 hour, carrying their scopes), refresh tokens (30 days, rotated on every use), all opaque and stored as SHA-256, looked up per request so revocation is immediate. Codes and refresh tokens are spent with one conditional update; **a spent one presented again revokes the whole grant** (`oauth.code_reused`, `oauth.refresh_reused`). **The device grant** issues a 256-bit device code and an eight-letter user code from RFC 8628's twenty consonants, both SHA-256 at rest and alive ten minutes, at most 100,000 waiting (`503` past it, a storage bound only); starting a flow refuses a request carrying `Origin` or a cross-site or same-site `Sec-Fetch-Site`, so a web page cannot recruit its visitors' browsers; the person types the code at the SPA's `/device` (`DEVICE_PATH`, the verification URI, signed in, charged thirty an hour per client address and per account, every unusable code one identical `400`, a `?user_code=` link prefilling but never submitting), which opens the existing consent screen for an authorization request stored beside the device code; entering the code makes the request the entering account's (`entered_by`, latest entry wins) and every other account reads and decides it as `404`, so a consent link passed on is no shortcut, and the decision consumes it, so two browsers of one account see one request decided once. Polls lock the device code's row and answer `authorization_pending`, `slow_down` (interval plus five seconds, with a second of slack for a timer's jitter), `access_denied`, `expired_token`, or tokens exactly once; a device code presented after its exchange, by a second holder or by a program retrying a lost answer (the server cannot tell them apart), revokes the grant (`oauth.device_code_reused`). The consent screen's request carries `delivery` (`redirect` with host and loopback, or `device`), and a device request shows the remote-phishing warning where the redirect address would be. **One resource, `<APP_URL>/mcp`** (`RESOURCE_PATH`), fixed rather than configurable because the metadata path, the challenge, the token binding, and the dev proxy must agree; a token for anything else is refused like an unknown one. **Scopes are the application's**, declared in Rust with `Scopes`, never hardcoded and never `offline_access`; a grant for no scopes still proves identity. `oauth_server::Bearer` is the resource-side extractor, the `CurrentUser` of a connected client, answering `401` with `WWW-Authenticate: Bearer resource_metadata=...`; a session cookie never satisfies it, and an account on an operator's temporary password is refused through it with the same `403` and `password_change_required` code `CurrentUser` answers, from one shared function. **Setting a temporary password and completing a password reset revoke every grant the account holds**, in the transaction that replaces the password, each audited as `oauth.revoked` by whoever caused it; a voluntary password change keeps them. Alex decided it. **`anubis::mcp`** serves Streamable HTTP at `/mcp` through **`rmcp`** (the official SDK, `server` and `transport-streamable-http-server` features only), both protocol eras, stateless and JSON, Host and Origin checked against `APP_URL`; the application registers tools in a `Registry` and the framework ships `whoami`. The framework enforces each tool's scopes and validates arguments against its input schema with `jsonschema`, because `rmcp` advertises schemas without enforcing them; both refusals are tool errors. Grants and revocations are audited (`oauth.granted`, `oauth.revoked`), the account lists and revokes connections (`useConnectedClients`, the starter's settings card), and `/.well-known`, `/oauth`, `/mcp` are reserved prefixes. Still to come: a `403` step-up from the MCP endpoint, an operator view of registered clients, a periodic sweep, and scope-filtered tool lists. See [oauth-server.md](docs/oauth-server.md) and [mcp.md](docs/mcp.md).
- **Uploaded images**: `anubis::images` is the one bounded decoder and the one screening seam. `images::decode` reads the format off the bytes and holds the header's dimensions to an edge limit and a pixel budget **before the decoder allocates**, so a small file declaring a huge image costs a header parse; the avatar upload reads its three bounds from `AVATAR_MAX_UPLOAD_BYTES` (5 MiB), `AVATAR_MAX_EDGE` (8192) and `AVATAR_MAX_PIXELS` (4096 squared). An application looks at every uploaded avatar before it is stored by implementing `images::ImageScreen` and mounting `auth::router_with(..., auth::Options::new().image_screen(screen))`; `auth::router` is `router_with` with no hooks, so nothing changes for an application that sets none. The screen sees the decoded source, uncropped, with its pixels as RGBA on demand, once per upload. `Verdict::Refuse` answers `400` with the code `image_refused` and a sentence that never says why; a `ScreenError` **fails closed** as `503` with `image_screen_unavailable`, logged at `ERROR`; either way nothing is stored and the old picture stays. Avatar uploads, removals and screen refusals are audited (`avatar.uploaded`, `avatar.removed`, `avatar.refused`) with the version token and never the image. See [api.md](docs/api.md#screening-uploaded-images).
- **Abuse limits**: `anubis::rate_limit` gives the auth endpoints in-process per-client budgets (GCRA, bounded map, no Redis) and answers `429` with `Retry-After`. The mail endpoints also charge the hashed target address, so rotating client addresses cannot bomb one inbox. Clients are the socket peer address unless `TRUSTED_PROXY_HEADER` names a proxy header, whose last entry wins. `RATE_LIMIT_DISABLED=true` is the development and test escape hatch. Limits are per instance; a shared store is future work. Behind the budgets, `anubis::auth::password::Hasher` is the single gate every argon2 computation passes through, admitting `PASSWORD_HASH_CONCURRENCY` (default 64, ~19 MiB each, so ~1.2 GiB) at once and shedding a caller as `503` after a five-second wait, because a burst spread across many client addresses meets no per-client budget and an unbounded blocking pool would OOM the container.
- **Testing**: unit tests beside the code, one narrative per area in `anubis/tests/`, plus a concurrency suite, an adversarial suite, and an ignored-by-default login-storm benchmark. Suites needing a database gate on `DATABASE_URL` and skip without it, and the Redis halves (the realtime fanout, the session store narrative) also gate on `REDIS_URL`. The session store narrative runs once per store and reads the store directly, because a Redis store that was never wired would otherwise pass as the Postgres default. `tests/support/TestDatabase` gives a test its own migrated database, created from a maintenance connection and dropped on `Drop`; the concurrency, adversarial, and benchmark suites use it, and the older narratives may adopt it as they need to count rows. Migration application takes a Postgres advisory lock, so two instances booting together (or two test threads) serialize instead of colliding in the catalog. See [testing.md](docs/testing.md).

This repo is open-source, public.
The main branch is production (stable), the develop branch is the working branch (unstable) that PRs push into.
If you're a Stakeholder (such as `navarrotech`) then you may push commits straight to develop.
Else you will be required to make a pull request for all other commits.

Stakeholders are responsible for promoting develop to main.
