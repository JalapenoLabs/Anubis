# Anubis

Anubis is an exciting, revoluationary project that's meant to be a framework that's extremely comparable to the (Ruby Bullet Train framework)[https://bullettrain.co].

However, it's core stack differs dramatically from Bullet Train. Here we use a rust-first ecosystem, with a full Rust backend.
Additionally, we use a React.js client side rendered SPA with HeroUI and TailwindCSS.
We don't use the same Ruby and SSR stack that Bullet Train uses, but offer as much as we can of everything else.

Additionally, we're tied closely to Jalapeno Labs and use:
- (Arsox Satellites)[https://github.com/JalapenoLabs/arsox-satellites] (for remote LLM job management)
- (UI Kit)[https://github.com/JalapenoLabs/uikit] (for re-usable UI components)
- (CLI)[https://github.com/JalapenoLabs/cli] (for utils like eslint standardization)
- (Brand)[https://github.com/JalapenoLabs/brand] (for Jalapeno Labs branding + styles + themes)
- (Github Actions)[https://github.com/JalapenoLabs/github-actions] (Shared, re-usable github actions workflow items and flows)

For full details, reference the @./README.md
We have a @./docs folder, for all documentation.
We use Github Issues for tracking tech debt and future work, and use milestones as "epics" for grouping a collection of tasks together.
We have @./bullet_train which has documentation of bullet train, in which we fully model and we submodule the main branch of their repository at bullet_train/bullet_train for reference.
We have a full research report about what bullet train is, generated by Claude web as a deep research job, outputted in @./bullet_train/bullet-train-deep-research.md for reference.
That report covers the framework's identity and history, current MIT/open-source licensing (including the fully open-sourced former Pro tier), modular gem architecture, Super Scaffolding code generator, team/membership multi-tenancy model, roles/permissions via CanCanCan, front-end stack (Tailwind + Hotwire + ERB), auto-generated REST API, developer workflow, deployment options, community health, real-world adopters, comparisons with Jumpstart Pro and vanilla Rails, demo resources, a categorized feature list, staged recommendations for a senior frontend engineer, and caveats around stale pricing sources and front-end lock-in.

# Blessed architecture decisions

These are decided and current. Full detail lives in @./docs (architecture.md, tenancy.md, scaffolding.md, api.md, server.md, webhooks.md, notifications.md, audit.md, billing.md, testing.md).

- **Backend**: Rust on tokio, Axum + tower + hyper. World-class idiomatic Rust is the bar.
- **ORM**: Diesel + diesel-async. Chosen for maximum compile-time typing; no stringly SQL, no runtime query surprises.
- **Datastores**: PostgreSQL required (system of record, sessions, durable job queue). Redis optional, for realtime pub/sub fanout and caching only, never durability; `REDIS_URL` is the whole switch.
- **Packaging**: one Cargo package (`anubis/`, library + CLI binary), one npm package (`frontend/`, `@jalapenolabs/anubis`), one thin starter template (`starter/`), all in this monorepo. No crate/package sprawl. The crate **publishes as `anubis-framework`**, because an unrelated 2019 crate holds `anubis` on crates.io, and **every visible name stays `anubis`** through Cargo's dependency renaming: `[lib] name` and `[[bin]] name` are `anubis`, the workspace declares `anubis = { path = "anubis", package = "anubis-framework", version = "..." }`, and a stamped application declares the same key over its own source, so `use anubis::` and the `anubis` command are untouched. Only the two commands that name a package to the registry differ: `cargo install anubis-framework` and `cargo update -p anubis-framework`. An `anubis` entry missing the `package` key resolves the squatter, so `anubis upgrade` refuses it and prints the line to write.
- **Releasing**: the crate and the npm package are **published, not consumed from git**, and they ship together from one tag under one version, because an application depends on both and a version naming half a release resolves for nobody. `.github/workflows/release.yml` fires on `v*`: it checks that the tag, `[workspace.package] version`, the `anubis` workspace dependency, and `frontend/package.json` all agree, and that the workspace dependency still renames the package `anubis/Cargo.toml` declares (`scripts/check-release-version.sh`), runs the full gates and the four drift checks, vendors the starter, packages, then uploads to crates.io and npm and cuts a GitHub Release with generated notes. Running the workflow by hand is a rehearsal: every gate, no upload. Neither registry allows republishing a version, so a half-finished release is recovered by a patch bump, never a retag; the GitHub Release is created last so the releases page never names a version only one registry carries. `CARGO_REGISTRY_TOKEN` and `NPM_TOKEN` are the two repository secrets. **The starter is vendored into the crate at publish time**: `anubis new` stamps from a template embedded at build time, and `cargo package` reaches nothing above `anubis/`, so `scripts/vendor-starter.sh` copies the committed tree to a gitignored `anubis/starter/` that `build.rs` prefers over `../starter`. An `include` list in `anubis/Cargo.toml` is what packages it (an include list makes cargo walk the filesystem instead of asking git, which would report a gitignored path as nothing), and manifests inside the packaged tree carry prefixed names (`Cargo.toml.vendored`, `workspace-Cargo.toml`, `backend-Cargo.toml`) because cargo prunes any directory holding a `Cargo.toml` as a nested package. `anubis/tests/packaging.rs` fails on either trap. See [ci.md](docs/ci.md#releases).
- **API contract**: REST at `/api/v1`, OpenAPI 3.1 via utoipa, generated TypeScript client (ky route functions + SWR hooks). No protobuf. The **application owns its OpenAPI document**: it declares the version's identity and merges the framework's half plus one line per scaffolded model, mounts the result with `api::v1::router_with`, exports it from its own binary, and generates the client with `anubis client generate-ts --from`. A platform token acts with its team's `admin` role, through the same compiled `roles.yml`.
- **Codegen**: Bullet Train's philosophy 1:1. Living templates (real compiling code, not a DSL), magic anchor comments, generated code is owned by the app. `anubis scaffold` generates backend + frontend + tests + docs in one command. `anubis eject <Component>` is the ownership escape hatch, Bullet Train's `bin/resolve --eject`: it copies a field component out of the installed npm package into `frontend/src/anubis/`, stamps its provenance, and rewires the app's imports. The ejectable surface is the field component library only; the API client, realtime client, and hooks stay framework-owned, because a copy of those forks a wire protocol rather than a style. The templates are `CreativeConcept`, `TangibleThing`, `GranularDetail`, `IncidentalLinkage`, `PeripheralNotion`, and `HypotheticalSenderWebhook` in `starter/`, compiled and integration-tested in CI; the anchor vocabulary is tabulated in `docs/scaffolding.md`. **Ownership runs three deep** (`Team`, `<Parent>,Team`, `<Parent>,<GrandParent>,Team`) and a fourth link is refused by name, because a depth is a living template rather than a flag: a name-for-name transform of a two-table query never produces a three-table one. The team is **read off the chain's root in the same query**, never denormalized onto the row, so a generated handler authorizes every hop as a join and a crafted cross-tenant path answers `404` at the first link it cannot reach. Every model owns a show page; a team-owned model also owns a list page and the navigation entry, and a nested model at either depth owns the section component its parent's show page renders. That nested show page is what the depth below it attaches to. Apps own their migrations and `schema.rs`; the starter backend is a library plus a thin binary so tests drive the real routers.
- **Associations**: `super_select` spells both of Bullet Train's, and the suffix decides which. Plural `<other>_ids` is a **has-many-through**, whose values are rows in a join model an earlier `scaffold join` created. Singular `<name>_id` is a **belongs_to**: a real nullable `UUID REFERENCES <targets> (id) ON DELETE SET NULL` column (an assignment is a pointer, not a dependency, so removing a person empties the field rather than being blocked by it), indexed, plus `valid_<attribute>s` and `<attribute>_labels` on the model, an options endpoint at `/account/teams/{team_id}/<owners>/options/<attribute>` (keyed by owner and attribute so two assignments never collide), validation before the insert, and a joined `<name>_label` on the view so screens render a name rather than a uuid. `{source=...}` is Bullet Train's modifier and means what it means there, namely where `valid_*` reads from: `team.memberships` is the framework roster (the default and only source for `class_name=TeamMembership`, Bullet Train's signature "assign to a membership, not a user" pattern, served by `TeamMembership::valid_for_team` and `labels_for` because a framework table cannot join an application one), `team.<others>` is the target model's own team-owned records (the default otherwise), and anything else is refused by name. A belongs_to target must be team-owned, and neither association can be declared at `scaffold model` time. Both `scaffold join` and `belongs_to` still refuse a side owned through a parent, at any depth, because one comparison is what decides whether a submitted id is this tenant's; lifting that needs a scope query per side and is separate work. **Deferred with a written design**: `buttons`/`options` fields with fixed translatable option lists, which is a separate item from `{source=...}`.
- **Background jobs**: durable Postgres queue, no Redis in the durability path. Enqueue rides on the caller's connection so it commits with the domain write. At-least-once delivery, quadratic retry backoff, then a `dead_jobs` table an operator reads. Jobs declare their own queue; a worker serves exactly the queues it has handlers for.
- **Webhooks, outgoing**: a team subscribes an HTTPS endpoint to event types under `/developers`; `anubis::webhooks::emit` writes a delivery row and a delivery job per subscriber **on the caller's connection**, so an event commits with the write that caused it. Event types are `<model>.<action>` (`created`, `updated`, `destroyed`); the catalog is the application's models, so the framework validates the shape. Payloads are the model's `View`, the same serializer `/api/v1` answers with. Delivery is the framework's own job on its own `webhooks` queue: HMAC-SHA256 over `<timestamp>.<body>` in `anubis-webhook-signature: v1=<hex>`, at-least-once, retried on the queue's backoff, then marked `dead`. Endpoint secrets are **encrypted** with `secret_box`, not hashed, because signing needs the raw value; they are shown exactly once. Generated models emit from the shared create/update/destroy functions, so both surfaces emit identically. See [webhooks.md](docs/webhooks.md).
- **Webhooks, incoming**: `anubis scaffold webhook <Provider>` generates a receiver for one third party. A received request is **stored first and processed afterwards**: the unauthenticated endpoint at `/webhooks/<provider>` writes one row (payload, headers, verified, received_at, processed_at, error) and enqueues its processing job **in one transaction**, then answers `200`, because a provider punishes a slow or failing receiver with retries and eventually disables it. The table is owned by nobody (a provider names no team), so it takes no `roles.yml` entry, no ownership chain, and no `/api/v1` surface. A failed signature check is **recorded in `verified`, never used to refuse the request**: rejecting at the edge destroys the evidence that explains what happened. `anubis::webhooks::signature::verify_hmac_sha256` is the provider-agnostic primitive every scheme ends in; the generated `verify_signature` wires the generic hex-of-the-body default and documents Stripe's, GitHub's, and Anubis's own. Processing runs on its own `incoming_webhooks` queue through `register_jobs` in the app's `lib.rs`. Receivers are deliberately **not rate limited**: the auth budgets are sized for humans, and refusing real events is what puts an endpoint on a retry schedule. Two functions are deliberate blanks the run names in its output, `verify_signature` and `act_on`. See [webhooks.md](docs/webhooks.md).
- **Realtime**: `anubis::realtime::Channels` publishes, browsers subscribe over one session-authenticated websocket at `GET /realtime`. Channel names are structured and carry their own authorization rule: `team:{team_id}:{topic}` admits the team's members, `user:{user_id}:{topic}` admits that user, and an unauthorized subscribe is refused exactly as a nonexistent one is. Fanout is in process by default (bounded by live interest, zero Redis); `REDIS_URL` switches it to Redis pub/sub so every instance's subscribers hear a publish. Nothing realtime is durable: clients refetch rather than replay. See [realtime.md](docs/realtime.md).
- **Notifications**: a framework-owned inbox, one row addressed to one person. `anubis::notifications::notify` is the single emission call and is `webhooks::emit`'s sibling: the insert rides the caller's connection, so a notice commits with the write that caused it. The row carries a machine-readable `kind` (`<subject>.<event>`), a stored English `title`/`body`/`href` (written once, because the record it names may later change or be deleted), `read_at`, and an optional `team_id`; a translated application looks its copy up by `kind`. Notifications are **addressed, not owned**, so there is no `roles.yml` entry, no ownership guard, and no `/api/v1` surface (a bearer token acts as a team, and a team has no inbox). The REST surface is three session-authenticated routes under `/account`: list (unread first, then newest, paginated, with the whole inbox's unread count), mark one read, mark all read; another user's id answers `404`. Realtime is a **ping, not a payload**: `notify` enqueues `PingRecipient` on the caller's connection and a `Pinger` on the `notifications` queue publishes `user:{user_id}:notifications` after the commit, because a publish inside the transaction would announce a notice that may roll back. The framework emits four notices: invitation received (to an invited address that already has an account, never carrying the claim token), invitation claimed (to the admins of what was joined), roles changed (to the member), and a webhook endpoint that stopped answering (to team admins, once per endpoint per day, leaving the endpoint active). **The scaffolder emits nothing**, the same line drawn for billing limits. The bell is `NotificationBell` in `@jalapenolabs/anubis`, mounted by the stamped `AppShell`, taking its four strings as `labels` and its navigation as `onNavigate` because the package imports neither i18next nor a router. Deliberately out of scope: email digests, per-type preferences, and reply-by-email. See [notifications.md](docs/notifications.md).
- **Audit log**: append-only, and on from the first request. `anubis::audit::record` writes one row through the caller's own connection, so an event commits with the write that caused it exactly as `webhooks::emit` and `notifications::notify` do; nothing in the framework updates or deletes a row, no endpoint offers either, and the table carries no `updated_at`. A row says where (`team_id` or `organization_id`, at most one, and neither for an account-level act such as a password change), who (`user_id` plus a **copied** `actor_name`, so a deleted account still reads), what (`action`, `subject_type`, `subject_id`, plus a copied `subject_label`), what moved (`changes` as `{field: {old, new}}`), and under which request (`request_id`). A handler takes the `audit::Context` extractor, which never fails, and attributes it with `.by(&user)` or `.by_application(&app)`; `Context::system()` records a null actor for a job. **Framework surfaces record themselves**: tenancy (organization and team create/rename/destroy, invitation created/claimed/revoked, member added/role changed/removed/left) and the auth-sensitive acts (password changed, TOTP enrolled/disabled, passkey added/removed, session revoked, account deleted). **Scaffolded models ride the shared create/update/destroy functions webhooks emit from**, so every generated model is audited with zero per-model code; the update's change set is `Changes::between` over the Diesel record, which is why a column `scaffold field` adds is audited the moment it exists. **Secrets are absent because they are never serialized**, not because anything strips them: a change set is computed from the same view `/api/v1` answers with, and credential events record an empty set. Actions are the bare lifecycle verbs for a model (`created`, `updated`, `destroyed`) and dotted verbs for the framework (`member.role_changed`), so the two vocabularies cannot collide. Reading is two routes under `/account`, outside `/api/v1` because the log is an operator's view rather than part of the versioned contract: `GET /teams/{team_id}/audit-events` (admin role, paged, filterable by `subject_type` and `actor_id`) and `GET /audit-events` (the caller's own account events, which is what makes the credential rows readable). The screen is `/teams/:teamId/audit-log`. Deliberately out of scope: retention, export, an organization roll-up screen, and diffing associations. See [audit.md](docs/audit.md).
- **Tenancy**: User -> TeamMembership -> Team -> Organization, plus OrganizationMembership for org-level roles. Resources chain ownership to a Team; assignments target TeamMemberships. Personal org + default team auto-created at signup. Billing attaches to the Organization.
- **Permissions**: single `roles.yml`, compiled to both a Rust authorization module and a TypeScript UI-affordances module.
- **Billing**: subscriptions attach to the **Organization**, and plans are configuration, not rows. `config/billing.yml` is compiled to a typed `PlanSet` and validated at boot exactly as `roles.yml` is: one plan per entry with a key, a name, per-interval Stripe price ids, and an app-defined `limits` map. Exactly one plan sells no prices and is the **free plan**, which is what an organization with **no subscription row** is on, so plan resolution is total. Stripe is the system of record for money: Stripe Checkout takes the purchase, the Stripe Billing customer portal takes every change after it, and `subscriptions` is the projection the app authorizes from (Stripe's status words verbatim, one live subscription per organization enforced by a partial unique index). The Stripe client is **hand-written** over the existing `reqwest` + rustls stack, six calls, because a generated SDK would model the whole API to serve them. `STRIPE_SECRET_KEY` is the switch: unset, everyone is on the free plan, reads still answer, and the writes answer `503`; production without it warns at startup. Endpoints are org-scoped under `/billing`, reading open to members and spending (and reconciling) gated on the `admin` or `billing` role. The **lifecycle** is framework-owned: Stripe posts to a framework-mounted receiver at `POST /webhooks/stripe-billing` (named so an app scaffolding its own `/webhooks/stripe` never collides), which verifies Stripe's `t=,v1=` signature strictly, refuses what does not verify with `400` storing nothing, stores what does in `stripe_billing_events` (event id unique, so a redelivery is one row and one job), and queues `ProcessStripeEvent` on the `billing` queue. Processing **reads the subscription back from Stripe** rather than trusting a possibly stale payload (a deletion is trusted, being final), and the upsert applies only when the event is not older than the one already applied (`subscriptions.stripe_event_at`), so out-of-order delivery cannot undo a cancellation. `STRIPE_WEBHOOK_SECRET` is the receiver's switch and is refused without the API key. Missed events are repaired by reconciliation, `Reconciler::reconcile` and `POST /billing/organizations/{id}/reconcile`, which reads the customer's subscriptions from Stripe and converges the rows. **Limits** are the plan's `limits` made real by `anubis::billing::Limits`: a limit written as a bare count is **hard** and its creation past the ceiling answers `409` naming the plan ("The Free plan's projects limit of 3 is reached. Upgrade to add more."); written as `{count, enforcement: soft}` it never refuses and the screen reports the overage. Bullet Train's split, kept. A limit a plan does not name is unlimited. **`seats` is the one limit the framework enforces itself**, at invitation creation, inside the invitation's transaction under the organization lock; a seat is a person counted once by email across org memberships, claimed team memberships, and live invitations. Every other limit is the application's to check at its own creation choke points with `limits.check(connection, org, name, held)` (the scaffolder does not write it: which model is metered, and under what name, is a product decision). **Per-seat pricing** is a `per_seat` flag on a price: checkout buys the seats in use, and every membership change queues `SyncSeats` on the `billing` queue, which tells Stripe the new quantity on Stripe's default `create_prorations` and writes the answer back. A flat-priced app never queues one. **`anubis billing generate-ts`** is the fourth generator, rendering `billing.yml` into `plans.generated.ts` (ordered plans, prices, limits, highlighted, free), drift-gated in CI like the other three, in the framework's workflow and in the stamped one. The **billing screen** is `/organizations/:organizationId/billing` (where Stripe returns the browser): current-plan card with status chip, `past_due` warning, cancel-at-period-end notice, period end and seat usage; the plans grid from the generated catalog; the portal link and a reconcile action, all three drawn only for `admin` or `billing`; a billing-disabled card when `STRIPE_SECRET_KEY` is unset; and the `?checkout=success|canceled` landing, trusted for nothing but a sentence. What the module deliberately leaves out: card forms, plan-change screens, invoices, tax, dunning email, proration policy, time-based usage limits, and any periodic reconciliation sweep. See [billing.md](docs/billing.md).
- **Serving**: one framework call, `anubis::server::serve`, owns production behavior; `main` only composes routers. It mounts liveness `/healthz` (no I/O) and readiness `/readyz` (database pool, 2s), and layers, outermost first: a server-minted request id returned as `x-request-id`, request tracing, security headers, opt-in CORS, and a 30s per-request timeout answering `503` in the `ApiError` shape. `SIGTERM` and ctrl-c drain in-flight requests for 25s, inside Kubernetes' default grace period. See [server.md](docs/server.md).
- **Security posture**: `nosniff`, `strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, and a full **content security policy** on every response, rendered once at startup: `default-src 'none'` with `script-src 'self'` (the Vite build emits no inline script and compiles nothing at runtime, so no `'unsafe-eval'`), `style-src 'self' 'unsafe-inline'` (React Aria and Motion write stylesheets into the document as they run and some carry no nonce, so a nonce would break what it did not cover), `img-src 'self' data: blob:` (the avatar picker previews through `URL.createObjectURL`), `font-src 'self'`, `connect-src 'self'` plus the websocket origin of `APP_URL` (named rather than trusting late-arriving CSP3 `'self'` matching for `ws:`), `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`. `CSP_ALLOWED_SOURCES` extends the seven fetch directives with host sources, validated at boot, and can never widen `default-src`, `base-uri`, `form-action`, `frame-ancestors`, or add a keyword such as `'unsafe-eval'`. The layer fills the header in rather than overwriting, so a handler may carry its own: exactly one does, the Scalar API reference at `/api/v1/docs`, which loads from a CDN. HSTS in production only, and only over https. CORS is strict same-origin until `CORS_ALLOWED_ORIGINS` names exact origins, validated at config load; credentials are never allowed cross-origin, so the bearer-token `/api/v1` surface is the cross-origin consumer and cookies stay same-origin.
- **Supply chain**: `cargo audit` and `yarn npm audit` run on every CI push, non-blocking for now; see [ci.md](docs/ci.md) for when they flip blocking.
- **Secrets at rest**: hashing is the default (passwords, tokens, recovery codes). Secrets the app must read back, such as TOTP seeds, are encrypted with pure-Rust AES-256-GCM (`anubis::auth::secret_box`) under `ANUBIS_SECRET_KEY`: base64 for 32 bytes, required in production, with a public development fallback so `yarn dev` stays zero-config. Stored values are versioned (`v1:<nonce>:<ciphertext>`). `anubis secret generate` mints a key (stdout carries the key alone, guidance goes to stderr) and `anubis doctor` warns when the variable is unset and fails when it holds a value that cannot be a key. Keys are zeroized on drop. Rotation is one-way by design: every value sealed under the old key stops opening, so TOTP enrollments are discarded and those users enroll again. A dual-key read path (previous key tried on failure, re-sealing as values are read) is future work.
- **Stamped applications**: `anubis new` hands over a repository that is ready to run and ready to merge. Beyond the manifests and pins it stamps `.github/workflows/ci.yml` (GitHub-hosted runners, fmt, clippy, tests against Postgres, the frontend job, and all three drift checks: roles, plans, and the API client), and `.env.example`. Development configuration is environment-driven: `yarn dev` copies `.env.example` to `.env` when absent, loads it with `dotenv-cli`, and hands the same file to `docker compose --env-file`, so credentials are written once. The database is named after the app and each stamp mints its own development password. Apps are private by default (`"license": "UNLICENSED"`); `--license mit` writes an MIT LICENSE. Templates ship no lockfiles: the app pins by committing `Cargo.lock` and `yarn.lock` in its first commit, under toolchains that `rust-toolchain.toml` and `packageManager` pin exactly. The monorepo starter runs the same `.env` flow, because it is the template.
- **Versioning and upgrades**: pre-1.0, a `0.x` minor may break and a patch never does, and every release ships notes naming the breaks and the steps they take by hand. The crate and the npm package ship as one release carrying one version, which `scripts/check-release-version.sh` cross-checks before the release workflow publishes anything. Applications take a release with **`anubis upgrade`**: it rewrites the `anubis` requirement in `backend/Cargo.toml` and the `@jalapenolabs/anubis` requirement in `frontend/package.json` (string surgery keeping each range operator, refusing a shape it does not recognize rather than guessing), runs `cargo update -p anubis-framework` and `yarn install`, re-runs all three drift generators in process so the CLI's own version is what regenerates, and prints the release notes URL. `--to <version>` names the target and never reaches the registry; `--dry-run` prints the plan and writes nothing. The structural promise is that **framework behavior lives in versioned dependencies, so an upgrade is never a starter-template merge**, which is Bullet Train's biggest documented cost. The trade is deliberate: the files `anubis new` stamped, the CI workflow and the Dockerfile among them, belong to the application forever, and a release that changes a template names the edit in its notes instead of merging it. An application tracking the framework from git has no version to bump and is told exactly that. The crate publishes as `anubis-framework` because `anubis` on crates.io is held by an unrelated crate published in 2019, so an application's entry must carry `package = "anubis-framework"`; the command refuses one that does not, and verifies the repository a crates.io entry declares before moving an application onto it. See [upgrading.md](docs/upgrading.md).
- **Abuse limits**: `anubis::rate_limit` gives the auth endpoints in-process per-client budgets (GCRA, bounded map, no Redis) and answers `429` with `Retry-After`. The mail endpoints also charge the hashed target address, so rotating client addresses cannot bomb one inbox. Clients are the socket peer address unless `TRUSTED_PROXY_HEADER` names a proxy header, whose last entry wins. `RATE_LIMIT_DISABLED=true` is the development and test escape hatch. Limits are per instance; a shared store is future work. Behind the budgets, `anubis::auth::password::Hasher` is the single gate every argon2 computation passes through, admitting `PASSWORD_HASH_CONCURRENCY` (default 64, ~19 MiB each, so ~1.2 GiB) at once and shedding a caller as `503` after a five-second wait, because a burst spread across many client addresses meets no per-client budget and an unbounded blocking pool would OOM the container.
- **Testing**: unit tests beside the code, one narrative per area in `anubis/tests/`, plus a concurrency suite, an adversarial suite, and an ignored-by-default login-storm benchmark. Suites needing a database gate on `DATABASE_URL` and skip without it. `tests/support/TestDatabase` gives a test its own migrated database, created from a maintenance connection and dropped on `Drop`; the concurrency, adversarial, and benchmark suites use it, and the older narratives may adopt it as they need to count rows. Migration application takes a Postgres advisory lock, so two instances booting together (or two test threads) serialize instead of colliding in the catalog. See [testing.md](docs/testing.md).
- **Roadmap**: M1 Foundation, M2 Tenancy, M3 API layer, M4 Scaffolding, M5 Ecosystem (webhooks, jobs, billing). Patterns are hand-built first, then automated by the scaffolder. GitHub milestones mirror M1-M5.

# Git

@./README.md

This repo is open-source, public.
The main branch is production (stable), the develop branch is the working branch (unstable) that PRs push into.
If you're a Stakeholder (such as `navarrotech`) then you may push commits straight to develop.
Else you will be required to make a pull request for all other commits.

Stakeholders are responsible for promoting develop to main.

Main should never be ahead of develop by any commits.
In practice: promote by fast-forwarding or merging develop into main, never by squash-merge. A squash mints a commit that exists only on main until someone merges it back, which is exactly the violation.
